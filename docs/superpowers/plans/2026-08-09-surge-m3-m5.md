- Correctness philosophy (from M0-M2): byte-exact GREEDY TOKENS, not byte-exact logits (GEMM/flash reduction order differs ~1e-7, fp16 KV adds ~1e-3, both absorbed by argmax). Metal reductions are fixed-tree, no atomics, no simd_sum (determinism underpins the token-exact gates).
- Q8_0 block = f16 scale + 32 int8; value = scale * int8. `sg_ref_matvec_q8` already exists in ref.c and is fixture-tested; new Metal Q8_0 kernels must match its accumulation order to the tolerance test_ref_ops uses.

GGUF arch string `qwen35`; ssm_a = -exp(A_log) (GGUF), v_heads tiled (GGUF); norms absolute on GGUF.
- 256K prefill is firmware-limiter-bound even fans-max: M5's 256K gate is FUNCTIONAL (ingest all tokens, coherent output), not a speed gate. Throughput belongs to M4. Every 256K prefill number is labeled limiter-shaped.

## Risks (from workflow, adopted)
fp16 KV can flip a genuine near-tie argmax (mitigated: f32 path keeps the ref gate; both mlx and llama.cpp use fp16/quant KV so f16 is the right apples-to-apples target). Flash-prefill softmax reduction order differs from decode (gate is token-level greedy equality; deterministic kernel; boundary can reuse the decode kernel if a flip is seen). Sequential DeltaNet chunk scan caps prefill speed (accepted; 256K is limiter-bound anyway; parallel scan is M4). Peak-RAM metric is phys_footprint (RSS), a "closest-available" cross-engine analog vs MLX's GPU-allocator peak (footnote it). Tokenizer BOS parity must be verified against llama.cpp's actual token count from cell-7's log. Parity vs mlx is class-level only (mlx used apply_chat_template + dynamic haystack); byte-identity is surge<->llama.cpp only.
